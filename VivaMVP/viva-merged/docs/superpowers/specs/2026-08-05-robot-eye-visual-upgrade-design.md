# 로봇 디스플레이 눈 비주얼 고도화 설계

날짜: 2026-08-05
대상 파일: `pi-server/eyes.py` (단독)
시안: https://claude.ai/design/p/2edddde4-b311-4bc3-80e0-50f6471ac9a4?file=Robot+Eyes.dc.html
(형태 변형 중 **둥근형** 채택, 2026-08-05)

## 배경

현재 Pi 는 480x480 원형 HDMI 패널에 초록(`#369B75`) 캡슐 두 개를 매 프레임
`pygame.draw.rect` 로 그려 `/dev/fb0` 에 직접 쓴다. 앱 `EyeAnimation.tsx` 의
비주얼을 그대로 옮긴 것이라, 폰 화면용 미니멀 캡슐이 그대로 로봇 얼굴이 됐다.

제품 목업(탁상형 로봇, 검정 구형 헤드)의 얼굴은 캡슐이 아니라 **흰 링 눈**이다.
목업 수준의 완성도로 올리는 것이 이 작업의 목표다.

## 목표와 비목표

**목표**

- 목업과 동일한 눈 형태: 두꺼운 흰 링 + 검정 속 + 흰 하이라이트 2개
- 살아있는 느낌: 눈동자 사케이드(시선 이동) + 변형 있는 블링크
- 4개 상태(`idle` / `calling` / `processing` / `conversation`) 각각의 표현 강화
- Pi Zero W(싱글코어 ARMv6)에서 **현행 이하의 CPU 사용량**
- 맥에서 실기기 없이 반복 개발 가능

**비목표 (이번 범위 아님)**

- WS 프로토콜 변경. 상태는 4개 그대로, 앱·FSM·`captureDecision` 손대지 않음
- 앱 `EyeAnimation.tsx` 반영. Pi 결과를 본 뒤 별도로 결정
- 감정 상태 추가, TTS 립싱크 연동

## 설계 결정과 근거

### D-1. 색: 흰 눈 / 검정 배경

목업 그대로. 기존 `GREEN` 상수는 이 파일에서 쓰이지 않게 되므로 제거한다
(테마 연결이 필요하면 앱 반영 시점에 다시 논의).

배경 검정은 이미 실기기 피드백(2026-08-03)으로 확정된 값이다 — 원형 패널
베젤과 이어져 화면 경계가 사라진다.

### D-2. 렌더링: 시작 시 프리베이크, 런타임은 blit 만

링 + 원 조합은 안티에일리어싱 없이 그리면 480px 패널에서 계단이 눈에 띈다.
pygame 의 `draw.circle` / `draw.rect` 는 AA 를 하지 않는다.

따라서:

1. 프로세스 시작 시 눈 하나를 **4배 해상도**(SRCALPHA)로 그린 뒤
   `pygame.transform.smoothscale` 로 1회 축소한다 → AA 된 서피스
2. 블링크용으로 **높이가 다른 12장**을 같은 방식으로 미리 굽는다
3. 상태별 변형(`conversation` 1.05배, `processing` 0.6 높이,
   `calling` 좌우 비대칭)도 굽는 대상에 포함한다
4. 런타임 프레임 비용 = 서피스 2장 `blit` + 좌표 계산

`smoothscale` 은 시작 시 수십 회만 돌고 루프에는 없다. 결과적으로 매 프레임
`draw.rect` 2회를 하는 현행보다 **런타임 비용이 낮다** — 12MP 촬영 인코딩과의
코어 경합(2026-08-04 실측: 7.6초 → 14.5초)이 악화되지 않는다.

베이크 총량은 (상태 변형 4종) x (블링크 12단계) 규모이며, 480 패널의 눈 한
쪽은 최대 ~150x190px 이므로 메모리는 수 MB 이내다.

### D-2b. `processing` 은 누르지 않고 위에서 잘라낸다

처음엔 눈 높이를 `0.6`(→`0.35`)으로 눌러 담았는데, 유니폼 스쿼시라 블링크
중간 프레임과 형태가 같아 "그냥 눌린 눈"으로 읽혔다.

대신 뜬 눈 스프라이트의 **아래쪽만 잘라 쓴다** — 윗변이 평평해져 눈꺼풀이
내려온 모양이 되고, 스쿼시와 형태가 겹치지 않는다. `subsurface` 는 픽셀을
복사하지 않는 뷰라 베이크도 메모리도 늘지 않는다.

절단 깊이는 큰 하이라이트(`GLINT1`) 아래여야 한다. 얕게 자르면 하이라이트가
절단면에 반쯤 걸려 혹처럼 남는다 — 상수 불변식으로 고정한다.

### D-3. 사케이드는 blit 좌표만 움직인다

링 안에서 동공만 따로 움직이려면 눈을 다층으로 나눠 매 프레임 합성해야 한다.
대신 **눈 전체를 몇 px 평행이동**한다. 두 눈이 같은 오프셋으로 움직여 시선이
수렴하고, 비용은 `blit` 좌표 정수 두 개다.

### D-4. 좌표계: 480 직접 사용

현행은 앱의 390 논리폭 좌표에 `S = 480/390 * 1.8` 을 곱해 쓴다. 시안이 480
좌표계로 나오므로 이 스케일 체인을 제거하고 상수를 그대로 픽셀로 쓴다.
`EYE_SCALE` / `S` 삭제.

### D-5. 반복 개발: `eyes.py` 자체에 창 모드

Pi 에 SSH 로 올려가며 값을 맞추면 반복 주기가 길다. 별도 프리뷰 앱을 만들면
실기기 렌더 코드와 어긋난다.

`python eyes.py --window` 로 맥에서 pygame 창을 띄운다. **분기는 출력 경로
뿐**이다 — `Renderer` 와 상태 머신은 실기기와 완전히 동일한 코드가 돈다.
숫자 키 `1`~`4` 로 상태를 전환한다(WS 없이).

## 시각 사양

### 눈 형태

각 눈은 세 겹이다.

| 요소 | 도형 | 색 |
|---|---|---|
| 바깥 | 라운드 사각형 `EYE_W` x `EYE_H`, radius `EYE_R` | 흰색 |
| 속 | 위 도형을 `RING` 만큼 inset, radius `EYE_R - RING` | 검정(배경색) |
| 하이라이트 1 | 원 `GLINT1_R`, 눈 중심 기준 오프셋 | 흰색 |
| 하이라이트 2 | 원 `GLINT2_R`, 눈 중심 기준 오프셋 | 흰색 |

### 상수 블록

모든 기하 수치는 `eyes.py` 상단 한 블록에 모은다. 아래는 HTML 시안 도구의
"값 복사" 출력으로 확정된 값이다(2026-08-05). 이후 조정은 이 블록만 고친다 —
코드 구조는 값에 의존하지 않는다.

```python
EYE_W, EYE_H, EYE_R, RING = 152, 175, 120, 21
GLINT1_R, GLINT1_X, GLINT1_Y = 24, -18, -29
GLINT2_R, GLINT2_X, GLINT2_Y = 7, 37, 33
GAP = 68
BLINK_MS = 4500   # 평균 블링크 간격. 실제는 ±1500ms 랜덤 = 3~6초
GAZE = 12         # 사케이드 가로 최대 오프셋(px). 세로는 GAZE * 2/3
BREATH = 3        # 브리딩 진폭(px)
```

불변식: `RING * 2 < min(EYE_W, EYE_H)`, `processing` 의 얕은 쪽 눈꺼풀이
`GLINT1` 아래까지 내려올 것, 그려진 모든 픽셀이 480 패널의 원(반지름 240)
안에 들어올 것. 셀프테스트가 검사한다.

`EYE_R` 은 절반을 넘으면 알약 모양으로 클램프된다(CSS `border-radius` 와 같은
동작). 확정값 120 은 `min(EYE_W, EYE_H)/2 = 76` 을 넘으므로 실제로 알약이다 —
불변식이 아니라 클램프로 처리한다.

`calling` 의 `!` 크기·위치는 `EYE_H` 비례로 잡는다. 고정 픽셀로 두면 눈을
키웠을 때 패널 원 밖으로 밀려난다(실제로 이 값으로 키우다 발생).

### 애니메이션

**사케이드** — `1.5~4초`마다 `±(GAZE, GAZE*2/3)` = `±(12, 8)px` 범위에서
목표 오프셋을 뽑고 `180ms` cubic in-out 으로 이동한 뒤 정지. 두 눈 동일 오프셋.

**블링크** — `BLINK_MS ± 1500ms` = 3~6초 간격, 매번 종류를 뽑는다.

| 종류 | 확률 | 타임라인 |
|---|---|---|
| 단일 | 70% | 감기 150ms → 뜨기 150ms |
| 더블 | 20% | 단일 → 90ms 정지 → 단일 |
| 느린 긴 것 | 10% | 감기 180ms → 유지 120ms → 뜨기 220ms |

감을 때 최소 높이 비율은 `BLINK_MIN = 0.02`. 처음 `0.06` 으로 잡았으나 링 눈은
캡슐과 달리 세로로 눌러도 흰-검-흰 줄이 남아 "덜 감긴" 것으로 읽혔다(시안
피드백). `0` 으로 두면 눈이 완전히 사라져 전원이 꺼진 것처럼 보이므로 얇은
선은 남긴다.

블링크는 `idle` / `conversation` 에서만 돈다.

**브리딩** — 현행 유지. 1.8초 내려갔다 1.8초 복귀, 진폭 3px.

### 상태별 표현

| 상태 | 표현 |
|---|---|
| `idle` | 기본 눈. 사케이드 전 범위, 블링크 3~6초, 브리딩 |
| `conversation` | 눈 1.05배. 사케이드 범위 절반 / 간격 절반(주시하는 느낌). 블링크·브리딩 동일 |
| `processing` | 위에서 눈꺼풀이 내려온 반쯤 감긴 눈(`LID`). 좌우 높이 차(`LID_TILT`)로 고민하는 비대칭. 시선은 위로 치우친 느린 타원(3초 한 바퀴). 블링크 없음 |
| `calling` | 왼눈 확대 / 오른눈 축소 비대칭 + 진입 시 감쇠 진동(현행 spring 근사 유지). 오른눈 우상단에 흰 `!`, 0.8초 주기 1.0~1.08 펄스 |

상태 전환은 현행과 동일하게 120ms 페이드아웃 → 180ms 페이드인.

## 구조

`eyes.py` 한 파일 안에서 책임을 나눈다. 파일 분할은 하지 않는다 — Pi 배포가
systemd 단일 유닛이고 현재 260줄 규모라 분할 이득이 없다.

```
상수 블록          기하·타이밍 수치 전부. 시안 값이 들어오는 유일한 자리
bake_eye(...)     4배 그리기 → smoothscale. 눈 서피스 1장 반환
EyeSprites        시작 시 (상태변형 x 블링크단계) 전부 구워 들고 있음.
                  frame(variant, blink_level) 로 조회
Blinker           블링크 종류 추첨 + 타임라인 샘플링 → 0~1 높이 비율
Gaze              사케이드 목표 추첨 + ease 보간 → (dx, dy). processing 은 원운동
Renderer          상태 + 시각 → 스프라이트 선택과 blit 좌표. 화면에 그림
WS 수신 스레드      현행 그대로
메인 루프          현행 그대로(크로스페이드, vsync, fbdev 쓰기).
                  --window 일 때만 출력 경로가 pygame.display 로 바뀜
```

`Blinker` / `Gaze` 는 시각을 받아 스칼라를 돌려주는 순수 함수형 객체다 —
`Renderer` 없이 단독으로 테스트할 수 있다.

## 에러 처리

- 폰트(`!` 글리프) 로드 실패 → `calling` 에서 `!` 만 생략하고 눈은 그린다.
  현행도 `SysFont` 를 쓰므로 동작은 동일하다
- `/dev/fb0` 열기 실패 → 현행처럼 예외로 죽는다. systemd 가 재시작한다.
  `--window` 모드에서는 fb 를 아예 열지 않는다
- 상수 불변식 위반 → 시작 시 `assert` 로 즉시 실패. 잘못된 값으로 굽고 나서
  화면이 깨진 채 도는 것보다 낫다
- WS: 현행 유지. 비JSON·미지 상태 무시, 응답 없음, 폰이 3초마다 재접속

## 검증

`python eyes.py --selftest` — pygame 초기화 후 베이크만 돌리고 종료한다.
프레임워크 없이 `assert` 만 쓴다.

1. 상수 불변식(위 "불변식" 항목)
2. 베이크된 스프라이트 장수가 (상태변형 x 블링크단계)와 일치
3. 블링크 최대 단계의 서피스 높이 < 최소 단계의 서피스 높이 (단조성)
4. `Blinker` 를 60초치 가상 시간으로 돌려 반환값이 항상 `[0.06, 1.0]` 안이고,
   블링크가 끝난 뒤 정확히 `1.0` 으로 복귀
5. `Gaze` 를 60초치 가상 시간으로 돌려 오프셋이 항상 설정 범위 안
6. 각 상태로 `Renderer.draw` 를 1프레임씩 호출해 예외 없이 끝나고, 그려진
   내용이 패널 원(반지름 240) 밖으로 나가지 않음. 검사는 **행 단위**로 한다 —
   전체 bounding rect 의 네 꼭짓점을 보면 왼눈의 x 와 `!` 의 y 처럼 실제로는
   비어 있는 좌표를 잡아 위양성이 난다

실기기 확인은 별도다: Pi 에서 `viva-eyes.service` 재시작 후 로그의 실측 fps
가 30 을 유지하는지, 촬영과 동시에 돌 때 인코딩 시간이 늘지 않는지 본다.

## 작업 순서

1. `--window` / `--selftest` 진입점과 출력 경로 분기 (지금 코드로 먼저)
2. 상수 블록 + `bake_eye` + `EyeSprites`
3. `Blinker` / `Gaze` + 셀프테스트
4. `Renderer` 를 스프라이트 기반으로 교체, 상태 4개 표현
5. 맥 창 모드에서 시안과 대조하며 상수 조정
6. Pi 배포 후 fps·촬영 경합 확인
